      Get started developing

      From nothing to your first mod built, linked and checked: about half an hour, most of it installing a compiler.

      What you need

      • Python 3.9 or newer and git. elekloader itself has no other dependencies.
      • The stock OS file for your device, from Elektron's support pages: the same file this page asks for. elekloader recognises each release by its hash.
      • The cross compiler, for a mod with code. On the Digitakt mk1 and the Digitone mk1 that is m68k binutils and gcc: on Debian or Ubuntu apt install binutils-m68k-linux-gnu gcc-m68k-linux-gnu; on Windows, the same inside WSL; on a Mac, with Homebrew, brew install m68k-elf-binutils m68k-elf-gcc, then export ELEKLOADER_CROSS=m68k-elf- (Homebrew's tools have that prefix). A mod that only changes a byte or two needs none.
      • Optional: digiemu, to run and check your build without a unit (Test before you flash).

      Your first mod

      1. Get the code and check it runs: 
        git clone https://github.com/irpina/elekloader
cd elekloader
python tests/test_units.py
      2. Copy the template, a complete mod that draws a small square in the corner of every screen. For the Digitakt II start from examples/hello-marker-dt2, for the Digitone II hello-marker-dn2, for the Octatrack hello-marker-ot, for the Models hello-marker-model: 
        cp -r examples/hello-marker my-mod
      3. Give it your own id in my-mod/mod.json (lowercase; it also prefixes your global symbols), then build it and the core for your device: 
        python -m elekloader.sdk.build my-mod --stock Digitakt_OS1.53.syx
python -m elekloader.sdk.build mods/core --stock Digitakt_OS1.53.syx
        Each prints BUILT and the .elemod it wrote (in the folder's out/).
      4. Check it the way every build is checked, then make a firmware file from it: 
        python -m elekloader.lint my-mod/out/my-mod-1.0.elemod --stock Digitakt_OS1.53.syx --with mods/core/out/core-4.0.elemod
python -m elekloader.patch --stock Digitakt_OS1.53.syx --mod mods/core/out/core-4.0.elemod --mod my-mod/out/my-mod-1.0.elemod --out test.syx --version TEST
        The file names are the ones the build printed. Or skip the command line: drop your .elemod on this page's Build view with your stock file.

      The rules in short

      • Subscribe, don't patch. If the core has an event for what you need, use it. If it doesn't and another mod could want the same thing, that's a core event to add: What is a core mod?
      • Ship no firmware. Call firmware routines by address; never copy Elektron's code into your sources.
      • One namespace. Prefix your global symbols with your mod's id, and keep the rest static.
      • Only the main OS changes, so the stock OS file always gets a unit back.

      The whole guide, with every command's expected output and every refusal message with its fix: Adapting your mod. Working with a coding agent? Point it at AGENTS.md: it has the rules, the commands and what "done" means.

      Contribute

      What is a core mod?

      The one mod every build has, and the reason mods from different people combine.

      Without it

      A mod changes the stock firmware at the places it needs: it replaces an instruction with a jump to its own code. Two mods that need the same place can't both have it, so they can't be in one build, and every mod has to find all its places again for each new OS version.

      With it

      The core owns the shared places once, for every mod, and offers them as:

      • Events a mod subscribes to: the UI tick, the screen, keys and encoders, SETTINGS, the audio render, MIDI, and more on each device. A handler can also take what it sees (a key, a CC) so the stock firmware doesn't.
      • Tables other mods add entries to: the Digitakt's SRC machines, the Digitone's Mod Menu.
      • Firmware exports: named firmware routines and variables (fw_…), so a mod that uses only those builds for every OS version the core supports without a port of its own.

      It also copies every mod's code into RAM when the unit boots, and gives the mods their share of it. Every linkable mod needs exactly one core for its device, and builds pick it for you.

      Companions

      A group of places only one kind of mod uses has a companion beside the core: machine-pages draws the Digitakt's SRC and LFO pages for machine mods, machines plays a machine mod's voice on the Digitone, seq-events turns the sequencer's steps into events, and on the Octatrack intercepts gives places a mod intercepts (MIDI notes, the CHROMATIC keyboard, locks, the project file) to the one mod that claims each. The to-do list counts them as core.

      Versions

      Each core keeps everything the one before it had, so a mod built for an older core links with the newest, and a build takes the newest: core 4.x on the Digitakt mk1, core-dn1 4.x on the Digitone mk1, core-ot 0.3.x on the Octatrack. The Digitakt II, the Digitone II (experimental), the Analog Rytm MKII, the Analog Four MKII and the Models have early cores (the tick, the screen, keys and encoders) with a lot left to add.

      Growing it

      Every event the core has came from a mod that needed it. When yours needs something the core lacks, build that part in the core's shape, in a file of its own, and open a pull request that moves it into the core: Growing the core says how. The to-do list is every place a mod still patches itself: each one a core event waiting to be written.

      Contribute

      Your first pull request

      Taking an entry from the to-do list to the leaderboard. You don't need to ask first, and a draft that says what it couldn't finish is a fine start.

      1. Pick an entry from the to-do list. A core event means the core has nothing there yet; move onto the core means a mod can use what the core already has (that change goes to the mod's own repository, and its shop update here is where you claim it).
      2. Open a draft pull request early, on irpina/elekloader, with a plain line in its description naming the entry: 
        Claims: digitakt-mk1@1.53:0x400d553e
        Others then see it's taken. Several ids on one line are fine.
      3. Build it in the core's shape: a file of its own in the core's folder, the core's names (ev_…, core_…, fw_…), the handler written down over the code, the unit behaving exactly as stock when no mod subscribes, and the address on every OS version the core supports. Growing the core has the checklist.
      4. Show it works: say in the pull request which tests ran (python tests/test_units.py always; the others need stock files), what you checked in digiemu or on a unit, and, best of all, a mod rebuilt on your event without its own patch.
      5. Mark it ready. A maintainer reviews and merges it, and the next build of this page puts you on the leaderboard, one point for each entry you claimed. The first merged claim on an entry takes it.

      A Claims: line inside a code block, a comment or a quote is an example and claims nothing. More in Claiming an entry.

      Contribute

      Test before you flash

      You can build, run and check most of it without a unit, and a unit always comes back.

      Every build is checked

      Before it writes a file, elekloader refuses any build that would change the bootloader, put two mods on the same bytes, or run out of the mods' RAM. python -m elekloader.lint runs the same checks on your mod alone, with the reason for each refusal.

      In an emulator

      digiemu runs the real firmware of the Digitakt mk1, the Digitone mk1, the Model:Cycles and the Model:Samples on Windows and on Apple silicon Macs, with a clickable front panel and live audio. You bring Elektron's file, as here.

      • Check firmware… takes your build's .syx and compares it with stock: it boots it, drives it through the screens and the sequencer, and ends with PASS or FAIL and the reasons.
      • Add your build as a firmware of its own to play it from the panel, or from a script with digiemu-console.exe --add FILE.syx.

      digiemu does not support the Octatrack, the Digitakt II, the Digitone II, the Analog Rytm MKII or the Analog Four MKII: there, test on a unit.

      On a unit

      Send your .syx with Elektron Transfer like any OS update (how to flash). The bootloader is never changed, so the stock OS file always gets the unit back: on a Digitakt mk1, Digitakt II, Digitone mk1 or Digitone II, hold FUNC while powering on and press TRIG 4 for OS UPGRADE, then send the stock file (on the Digitakt II and Digitone II, over MIDI DIN, not USB); on an Octatrack, hold FUNC and press TRIG 3, and send it over 5-pin MIDI (recovery).

      Never made one before?

      Make your own mod!

      You don't have to be a programmer. Tell an AI coding agent what kind of sound you want: it writes the code, checks it on your computer, and builds a firmware file you can try on your unit. This page is what a mod is, what you need, what to ask, and what to expect.

      Just want your own picture on the boot screen? The Splash screen maker makes that mod right here, from a PNG or a GIF, with no agent and no setup.

      What is a mod?

      A mod is a small file (.elemod) that adds something to your Elektron's operating system: a new sound machine, an effect, a change to a screen. You pick mods in the Mod Shop, and Build Firmware combines them with Elektron's own OS file into a normal update (a .syx) that you send to your unit like any other. Making a mod means making one of those small files.

      The easiest first mod: a sound machine

      A machine is a new sound source: its name, its knobs, the pages they sit on, and the code that makes the sound. You write it once, in a few dozen lines of C, and the same file builds for the Digitakt (OS 1.54), the Digitone and Digitone Keys (OS 1.44) and, without sound code for now, the Digitone II (OS 1.12). Your agent writes those lines; you decide what it should sound like. This part of elekloader (the SDK) is an alpha: it can change, and a mod may need rebuilding when it does.

      Wanting something else, such as an effect, a new screen or a change for another device? Tell the agent that, and it will start from the right template. The developer's guide is the longer route.

      What you need

      • A coding agent that can run commands on your computer (Claude Code, Codex and others). It does the installing and the typing; you stay in charge.
      • Python 3.9 or newer and git. The agent can install them and the rest; setup is the part that takes longest.
      • Your device's stock OS file, the one you download from Elektron. Where to get it. It stays on your computer: never put it in a repository.
      • A cross compiler, to turn the C into code your unit runs. The agent installs it (on Windows it works inside WSL).
      • A backup plan: the stock OS file also puts your unit back as it was. How to flash, and how to go back

      Start here: paste this to your agent

      I'm new to this and want to make my first elekloader mod: a new sound machine for my Elektron. I'm not a programmer, so explain things plainly and do the setup for me. Start by asking me which device and OS version I have and what kind of sound I want. Then clone https://github.com/elekloader/elekloader, read AGENTS.md and docs/SDK.md, and install whatever is missing (Python 3.9 or newer, git, the ColdFire cross compiler; on Windows use WSL). Copy examples/sdk-hello-world as the starting point, write my machine in C, and run it on my computer with python -m elekloader.sdk.sdk_alpha_host before you build anything. Ask me where my stock OS file is (the .syx I downloaded from Elektron); never copy it into the repository or commit it. Build, lint and patch as docs/SDK.md says, then give me the .syx and plain instructions for trying it, including how to get back to stock. Never flash my device yourself. When I'm happy with it, help me put the mod in its own GitHub repository and send me to the Submit your mod tab.

      What happens next

      1. The agent asks you which device and OS you have, and what you'd like to hear: "a fat saw with a tune knob", "a noisy hi-hat", "something that sounds broken".
      2. It writes your machine and runs it on your computer. That check prints each knob's label and the sound's level and pitch (no audio yet), so mistakes show up before anything is built.
      3. It builds a firmware file from your stock OS file, your mod and the pieces it needs, and checks that they fit together. You get a .syx.
      4. You try it. First in the emulator if you like (Test before you flash), then on your unit. The sound is the part only you can judge, so tell the agent what to change and it will rebuild.
      5. You share it, when it's good: Submit your mod.

      Good to know

      • Only the main OS changes. The bootloader stays stock, so the stock OS file always gets a unit back. Flashing custom firmware is still at your own risk, and elekloader isn't affiliated with Elektron.
      • Ask the agent to explain. "What does this line do?" and "what could go wrong on the unit?" are good questions at any step.
      • Say what you haven't tested. If it only ran in the emulator, say so when you share it: "not yet on a unit" is a fine answer.

      Submit your mod

      Put your .elemod files in a release on your own GitHub repository, send one form, and a bot checks them and opens the pull request for you. No files go into elekloader's repository, and there are no evidence files or screenshots to make.

      Using an AI agent?

      Most people do. Paste this to your agent. It can do the whole thing from the command line: build, release, submit, and read the bot's answer.

      Submit my elekloader mod to the Elekloader Shop. First read the section "Using an AI agent" of https://github.com/elekloader/elekloader/blob/main/docs/SHOP.md and follow it. In short: build the .elemod files for each OS version I support, publish them in a GitHub release on my repository, then open a "Submit a mod" issue on elekloader/shop with gh issue create. A bot checks the issue and opens the pull request, so don't open one yourself. Before you publish or submit anything, show me the release notes, the summary and the "Tested on a unit" text, and wait for my OK: I am the one declaring that I wrote the mod (or its licence lets it be passed on) and that the files hold no Elektron firmware. Then read the bot's comment on the issue and fix whatever it refuses.

      The agent needs GitHub's command line tool (gh), signed in as you. You stay in charge of two things it will ask you: what ran on a real unit, and that the mod is yours to share.

      What you need

      • Your .elemod files, one for each OS version the mod supports. Adapting your mod builds them.
      • A GitHub repository to hold them in a release (a pre-release is fine for a beta).
      • A licence the shop can pass on: MIT, GPL, LGPL, BSD, Apache-2.0, MPL-2.0, ISC, 0BSD, CC0 or the Unlicense, named in your mod.json or on the form.
      • No Elektron firmware in the files: your mod's own code only.

      The steps

      1. Release. Publish a GitHub release on your repository with the .elemod files attached. One command builds, releases and prints the form's address: 
        python -m elekloader.sdk.publish my-mod --stock Digitakt_OS1.53.syx --no-browser \
    --summary "One sentence." --tested "What ran on a unit, and what not yet."
      2. Submit. Open the form (or have your agent run gh issue create): your repository, the release tag, a one-sentence summary, and what you've tested on a unit. "Not yet" is a fine answer.
      3. Read the bot's comment. It checks each file's checksum, licence, OS, and that the shop has what the mod needs. If it refuses something it says why; fix it and edit the issue, and it checks again.
      4. A maintainer merges the pull request the bot opened, and the next deploy puts your mod on the Mod Shop.

      Open the Submit a mod form

      After it's in

      Publish a release, and the shop takes it. Every day the shop looks for newer releases of the mods it lists and takes the newer files, with the same checks. Updates are on by default. To decide yourself which releases go in, tick the form's Updates box, or put Shop auto-update: off in a release's notes. Lines Shop summary: … and Tested on a unit: … in the notes change your card's text.
